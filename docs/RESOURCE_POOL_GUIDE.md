# 资源池治理规范

## 与底座的映射

| 业务概念 | New API 组件 | 使用规则 |
| --- | --- | --- |
| 资源实例 | `Channel` | 一个上游账号、代理端点或多 Key 集合对应一个渠道；密钥只保存在后台。 |
| 模型能力 | `Ability` | 由渠道的模型列表和分组生成；每个公开模型至少绑定一个启用能力。 |
| 故障摘除 | 渠道状态/自动禁用 | 健康检查失败时自动禁用，恢复后再启用；人工禁用不能被自动恢复覆盖。 |
| 负载均衡 | `Priority` + `Weight` | 先按优先级分层，再在同层按权重随机选择；权重越高承接比例越高。 |
| 会话粘性 | `channel_affinity` | 只使用脱敏指纹作为缓存键；缓存内容是内部渠道 ID，对用户响应不可见。 |
| 运营分组 | `Group` / `Tag` | 用于环境、租户、成本中心和灰度发布，不把供应商名暴露给用户。 |

## 建议的后台配置

1. 为每个公开模型创建一个稳定的“模型别名”，例如 `standard-chat`、`reasoning-pro`；别名与真实模型名、渠道类型和上游 URL 分离保存。
2. 为别名至少配置两个资源实例（生产建议跨供应商/跨区域），设置优先级、权重、超时、最大并发和自动禁用阈值。
3. 先用高优先级资源承接请求；只在超时、限流、余额不足或明确的上游 5xx 时切换。鉴权失败、请求参数错误和内容策略拒绝不应盲目重试。
4. 为每个资源配置健康检查模型和最小测试请求。测试结果只写入管理员审计和指标，不回传给用户。
5. 灰度发布通过独立分组/标签完成，观察成功率、P95、平均成本和熔断次数后再调整权重。

## API 导入与模型入池

后台的“创建渠道/编辑渠道”流程支持从上游 API 拉取模型列表。管理员填写地址和凭据后点击“获取模型”，选择模型并保存渠道；保存时系统会把模型列表写入渠道配置，并重建对应的 `Ability` 记录，因此每个模型会自动进入所选分组的资源池。后续新增渠道只需重复该流程即可扩充同一模型池，不需要手工逐个创建模型。

导入流程不会把上游模型列表直接暴露给普通用户；用户侧只看到已发布的模型目录和公开别名。拉取失败、鉴权失败或模型列表为空时，渠道不会被当作可用资源写入生产路由。

## 对外隐藏要求

- 对外 `/v1/models` 只返回模型别名、能力和价格；禁止返回渠道名称、真实上游模型、基础 URL、地区、余额和 Key 片段。
- 所有上游错误统一映射为公共错误码 + request ID；内部日志保留渠道 ID 和失败类型，绝不记录 Authorization、完整 prompt 或响应体。
- 流式响应开始后不能切换渠道；切换只发生在响应尚未写出或明确可安全重试的阶段。
- 管理员查看明细需要 RBAC 和二次认证；普通用户的消费明细只显示模型别名与计量，不显示资源池信息。

## 当前缺口与后续实现顺序

1. 增加资源池视图：按模型别名聚合渠道、健康状态、权重、优先级、近 5 分钟成功率和 P95。
2. 增加策略校验：禁止公开模型没有可用资源、禁止所有资源权重为零、禁止把人工禁用资源自动恢复。
3. 增加熔断参数配置和变更审计；参数按模型别名生效，不允许用户请求覆盖。
4. 增加脱敏回归测试，验证错误响应、模型列表和计费日志都不会泄露上游身份。
